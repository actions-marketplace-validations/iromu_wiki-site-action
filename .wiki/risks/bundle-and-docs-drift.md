# Bundle rebuild and docs drift

Two fragile areas worth knowing before editing.

## The `dist/index.cjs` bundle must be rebuilt and committed

The action executes `dist/index.cjs` (see `action.yml` → `runs.main`), **not**
`index.js`. That file is an esbuild bundle generated by:

```sh
npm run build   # esbuild index.js --bundle --platform=node --format=cjs --target=node24
```

**Rule:** after changing `index.js` or anything under `lib/`, re-run
`npm run build` and commit the new `dist/index.cjs`. If you skip this, the action
silently runs stale code — your change is live in the source but not in the
bundle, so the deployed site will not reflect it. Do not hand-edit
`dist/index.cjs`.

**Why:** the bundle is committed precisely so the action needs no install step
at run time. That convenience means the committed artifact is the source of
truth at runtime.

**How to apply:** treat `dist/index.cjs` as a build output in the same category
as `node_modules`-generated files — regenerate, never edit.

## Docs still describe the old publish behavior

`v2` made the action build-only and removed the `gh-pages` publish step (commit
`9ef5745`). But the `package.json` description still reads *"…publishes it to
the gh-pages branch"* and the README still frames deployment as the action's
job. The actual behavior (build to `out-dir`, then the consuming workflow
publishes via `actions/upload-pages-artifact` + `actions/deploy-pages`) is
described correctly in the README body and in [[how-it-works]].

**Why:** the stale one-line description can mislead a reader into expecting the
action to deploy.

**How to apply:** if you touch the docs, align the `package.json` description
with the build-only reality. The code is correct; the description lags.

## Related

The smoke test (`test/smoke.js`) is the safety net: it asserts page count,
`[[wikilink]]` resolution, broken-link detection, asset presence, nested-page
`../` asset roots, and source-chip URLs. Keep it green — it is the only test.
